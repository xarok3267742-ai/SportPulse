# Выпуск подписанного Event Pack

Secure Envelope отделяет поставку данных от Android-приложения: приложение содержит только публичные ключи, а приватный ключ никогда не попадает в APK, репозиторий или облачную сборку.

## Локальная разработка

Локальный RSA-ключ находится в `.local/event-pack-dev-private.pem`, имеет права `0600` и исключен из Git. Соответствующий публичный ключ зарегистрирован как `sport-pulse-local-dev-2026` для источника «Локальный тестовый пакет».

Этот ключ нужен только для воспроизводимого QA. Интерфейс и PNG всегда называют его development-ключом.

## Подключение поставщика

1. Поставщик генерирует RSA-ключ минимум 3072 бит на изолированной машине или в HSM.
2. Приватный ключ остается у поставщика. Команде приложения передаются только DER/PEM-публичный ключ, стабильный `keyId` и точное разрешенное имя `source`.
3. Публичный ключ добавляется в `TrustedEventPackageKeyRegistry` с окружением `PRODUCTION`.
4. APK с новым публичным ключом проходит проверку до начала подписанных поставок.
5. Поставщик подписывает точные UTF-8 байты payload. Повторное форматирование после подписи запрещено.
6. Перед публикацией envelope независимо проверяется вторым процессом и импортируется в контрольную сборку.

## Ротация

1. Сначала выпускается приложение, доверяющее старому и новому публичным ключам.
2. После достаточного обновления клиентов поставщик начинает подписывать новым `keyId`.
3. Переход ключа появляется в «Радаре обновлений».
4. Старый публичный ключ удаляется только в следующем приложении после завершения окна миграции.

Production-ключ не может быть заменен development-ключом или неподписанным файлом. Явный переход к локальным данным требует ручного возврата к демо-каталогу.

## Компрометация

Офлайн-приложение не может мгновенно получить список отзыва. При подозрении на утечку нужно:

1. остановить выпуск пакетов;
2. выпустить обновление приложения без скомпрометированного публичного ключа;
3. зарегистрировать новый `keyId`;
4. опубликовать временные метки инцидента и диапазон затронутых `packageId`;
5. не переиспользовать прежний ключ.

Криптографическая подпись подтверждает владельца ключа и неизменность payload, но не заменяет договор с поставщиком, проверку первичных спортивных источников и редакционную ответственность.
